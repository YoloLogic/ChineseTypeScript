## 二、机制（三句话）

1. **声明层**：把上游 `lib.*.d.ts` 的成员**增补**一份汉语声明（`interface X { 汉语名(...): ... }`），
   接口名与类型**原样保留** → 英文用法零影响、类型检查通过、产物仍是标准 JS。
2. **emit 层**：printer 在**成员位置**把汉语名改写回英文规范名（`甲.追加(4)` → `甲.push(4)`），
   所以**产出的 JS 与英文写的一模一样**。全局名在任何引用位置改写。
3. **手工声明**：`tests-chts/zhstdlib/汉语标准库.d.ts` 放类型别名、全局 `声明变量` 与手写函数；
   其余全由生成器产出（`-成员.generated.d.ts`）。

## 六、下一步（按性价比排序）

### 1) 符号感知（关键路径，必须先做）

**为什么**：现在的 emit 改写在**成员位置**一律替换。于是「用户自己也有一个叫 `描述` 的成员」时，
`甲.描述` 会被改写成 `甲.description` → **运行时才炸**。已**发作三次**（教程 `编号`、`demo_ident` 的
`描述` 与 `端口`）。也因此，`code`/`color`/`content`/`count`/`event`/`file`/`input`/`link`/`page`/
`path`/`pattern`/`user`… 这**上百个高频通用名词至今没敢翻**。

**怎么做**（`规模化方案.md` 六·七 有完整方案）：让 **checker** 在解析时把「这是标准库成员」的节点打上
标记（例如 emit 标志位 `EFChineseStdlib`），printer **只改写被标记的节点**，不再靠文本位置猜。
**必须同时新增一条判据**：用户自己定义了同名成员时，那一处**不能被改写**（现在这条是缺的）。
**两条失败教训**（六·七·附）：printer 侧「按文件作用域猜」无效；命名空间嵌套的改写会产生孤儿成员。
