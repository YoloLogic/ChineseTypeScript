# 标准库汉化 · 规模化方案（执行规格）

> 现状：**试点 42/7687 条**已端到端跑通（见 `README.md`）。
> 本文是把试点扩到全量 7687 条的**执行规格**，供下一轮照着做。

## 一、为什么不能「从译名表直接生成汉语声明」

译名表只有 `kind / english / 译名` 三列，**没有签名**：

```
member   push   追加      ← 只有名字，没有 `(...items: T[]): number`
```

类型信息（）在**上游 lib 里**。所以汉语声明只能靠**转换上游 lib**得到 ——
这正是用户最早的方案：**复制上游 lib，按表把声明改名，签名原样保留**。

## 二、转换器设计（`tools/gen_zhstdlib_lib.ps1`，待实现）

**输入**：`tsc/internal/bundled/libs/lib.*.d.ts`（107 个）+ `stdlib/名字清单.tsv`（译名）
**输出**：`tsc/internal/bundled/libs/lib.zh.d.ts`（生成物，勿手改）

### 2.1 只做「改名」，不改结构
按译名表把**声明名**替换成汉语名，其余（类型、泛型、交叉引用、注释）**逐字保留**：
* `interface Array<T>` → `interface 数组<T>`
* `push(...items: T[]): number;` → `追加(...项: T[]): number;`（**参数名也该改**，但可后置）
* 引用处同步：`Array<T>` → `数组<T>`（**全 lib 的交叉引用都要跟着改**）

### 2.2 最难的三处（必须先解决再动手）
1. **交叉引用**：`ReadonlyArray`/`ArrayLike`/`PromiseLike` 等互相引用；
   改名必须**全局一致**，否则生成物里会出现悬空名字。
2. **重载与多行签名**：`filter`/`reduce` 有重载且跨多行 —— 行级替换会切坏；
   需要**按声明块**（而不是按行）处理。
3. ~~**同名不同义**~~ —— **已想清，不是问题（2026-10-08）**：
   emit 改写做的是「**汉语名 → 英文名**」的映射，与接收者类型无关。
   只要译名满足「**一英一汉、全局唯一**」（一个英文名只对应一个汉语名），
   那么 `Array.map` 与 `Map.map` 共用 `映射`、`Array.length` 与 `String.length` 共用 `长度`
   都是**正确**的。真正会出问题的只是「同一个汉语名对应两个不同英文名」，
   而这由唯一性定则直接排除。→ **译名表保持按名字全局，不分域**；
   生成器要加一条守卫：**英文名与汉语名都不得重复映射**。

### 2.3 英文别名（用户要求「两者都认」）
**不要把英文 lib 删掉**：保留上游 lib 原样，汉语 lib **只增不改**（`interface 数组` 是新声明、
`interface Array` 仍在）。这样英文用法与汉语用法天然并存 —— 试点就是这么做的。

## 三、还要定的两件事

1. **汉语声明怎么自动加载**：试点要手写 `/// <reference path="汉语标准库.d.ts" />`。
   规模化要让它随 `--lib` 自动进编译（改 bundled libs 的登记处）。
2. **emit 改写要不要符号感知**：现在是**文本级**（全局名引用位 / 成员名仅成员位置），
   `Node.Symbol()` 只对声明节点有效，引用位拿不到符号。
   要真感知需把 checker 的解析结果记到节点/emit flag（`EmitResolver` 是现成扩展点）。

## 四、守卫（每步都要有，且要能失败）

| 守卫 | 判据 |
|---|---|
| 译名表 ↔ Go 表同步 | `tools/gen_zhstdlib.ps1 -Check`（已做，判定第⑦项） |
| 译名表 ↔ lib 生成物同步 | `tools/gen_zhstdlib_lib.ps1 -Check`（待做） |
| 生成物自身健全 | 生成的 `lib.zh.d.ts` 必须**能通过编译**；名字无悬空 |
| 端到端 | `judge_zhstdlib.ps1` 扩为全量样例（类型检查 → 标准 JS → node 真跑） |
| 英文零回归 | `judge_oss 600/600` + `judge_gotest`（现成） |

> ⚠ **判据卫生（试点里连撞三次）**：断言「产物里不含汉语标准库名」时，必须限定成
> **属性访问形式**（`\.名字`），否则会被**字符串字面量**误判 —— 例如 `console.log("找序号=" + ...)`
> 里的 `找序号` 是用户文本、**本就不该被改写**，用裸名字去匹配会假报失败。

## 五、建议的推进顺序（每步一提交）

1. **译名唯一性守卫**：给译名表加一条机器守卫 —— 英文名与汉语名都必须**一英一汉**
   （同一个汉语名不得映射到两个英文名，反之亦然）。这是「不分域」成立的前提。
2. **转换器（先只处理 `interface` 块改名，不做交叉引用）**：产出 `lib.zh.d.ts`，拿 **ES 核心少量接口**（`Array`/`Math`/`String`）验证能编译。
3. **补交叉引用改写**，直到整个 ES 核心能编译。
4. **自动加载**：让汉语声明随编译进包。**侦察结论（2026-10-08）**：
   * 上游 lib 的嵌入产物是 `tsc/internal/bundled/embed_generated.go`（内容）与 `libs_generated.go`（名单），
     由 `tsc/internal/bundled/generate.go` 生成 —— 「加一个 lib」要走**生成器**，不能手改嵌入文件；
   * 还要让它进**默认 lib 集合**（默认集合由 target/`--lib` 推出）；
   * 风险：声明是增补式的，但要重跑上游 Go 测试全集（`judge_gotest`）确认没有意外冲突；
   * 这是**多步编译器改动**，建议单独一轮、上下文充足时做。
5. **扩到 DOM**（2052 全局 + 4695 成员）。
6. **发行包**：把汉语 lib 与文档打进 zip（阶段④）。
   ⏸ **暂不做**（2026-10-08 决定）：汉语声明还没做到**随编译自动加载**，
   试点要用户手写 `/// <reference path="汉语标准库.d.ts" />`；在自动加载落地前把半成品打进发行包，
   只会让用户以为「开箱即用」。等第 4 步（自动加载）完成再打包。

## 六、运行纪律（血泪）

* ⚠ **别每轮跑全量回归**：`run_all` 会把上游 Go 测试全集编译两遍，
  **Go 构建缓存**（`GOCACHE=E:\gopath\build-cache`）会迅速膨胀 —— 2026-10-08 实测堆到 **121.55 GB**，
  直接把 E: 盘撑满、`git commit` 报 `Out of diskspace`。
  处置：`Remove-Item E:\gopath\build-cache -Recurse -Force`（**只影响下次编译速度，不需联网重下**；
  模块缓存 `pkg` 只有几十 MB，别删）。建议：**阶段性**跑全量，别每轮跑。
* 该现象**第二次出现**（第 158 轮）：连续全量后 `judge_gotest` 报 `modulespecifiers` 多出，
  但**单独重跑即通过**。为不再靠人判断，`judge_gotest` 现在会**对允许清单外的失败包单独复验一次**：
  单跑通过 → 判为环境性抖动（打印 `[复验]` 与 `[!]` 提示，不计入回归）；单跑仍失败 → 照常报红。
  这样**真回归必复现、环境抖动被证据排除**。

## 六·五、吞吐现实与三条出路（2026-10-08 交用户决定）

**现实**：生成器打通后，加译名的成本已降到「表里一行 + 重新生成」，但**翻译本身**仍是人手活。
实测每轮稳定 +10~16 个名字，而清单有 **7687** 个 —— 若目标上限 256 轮，
**照此打法不可能在轮次内完成**（需 ~500 轮）。

**三条出路**（等用户裁定）：
1. **收窄目标**：只做「高频子集」（ES 核心 + 常用 DOM ≈ 1000 名），可在目标内做完；
2. **先做自动加载**（第 4 步），让功能先可用；译名改由**脚本/社区**补（例如开放一份译名 CSV 供 PR）；
3. **维持**：慢速长期推进，接受目标长期挂着。

> 注意：**不要**为了提速而「机器拼词」直接产出译名 —— 本项目对译名有硬要求
> （2–6 汉字、一汉一英、与中文 C++ 项目同词同义），拼词结果质量不可控，会把判据逼成橡皮图章。

## 六·六、【严重】文本级改写的误伤 —— 符号感知是**必需**，不是可选

**实证（2026-10-08，本项目自己的教程被打破）**：
给 `id` 定名「编号」后，`judge_tutorial` 立刻变红 ——
例子 `06-类型与接口.ts` 里用户自定义的属性 `只读 编号: 数字 = 7`，
其读取 `猫甲.编号` 被 emit 改写成了 `猫甲.id` → 运行输出 `只读编号=undefined`。

**为什么严重**：改写是**按名字文本**做的（只在成员位置），**不看这个名字到底解析到谁**。
而中文用户给自己的成员起名时，最常用的正是**通用名词**：`编号`/`名称`/`状态`/`数据`/`长度`/`类型`…
—— 恰好是标准库译名的高频词。于是**用户越自然地命名，越容易撞车**，而且**产物静默出错**（运行时 undefined，不是编译报错）。

**结论与优先级**：
* 「给常用名词定译名」这条路**必须先解决符号感知**，否则等于给用户埋雷；
* 符号感知 = 在 checker 解析出成员符号后，把「确实来自我们汉语声明文件」的节点标出来，
  emit 只改这些节点（`EmitResolver` 是现成扩展点；`Node.Symbol()` 对引用位无效，需要在 checker 里记）；
* 在符号感知落地前：**暂缓继续给「通用名词」定译名**（专用名如 `createLinearGradient` 更安全）。

## 六·七、符号感知：实现方案（可执行，下一阶段主线）

**目标**：emit 只改写「**确实解析到我们汉语声明文件里的成员**」的引用；
用户自己声明的同名成员**一个字都不动**（见 六·六 的实证）。

**数据流**
1. checker 在解析 `X.名` / 全局名引用时，手上**已经有符号**（它刚刚做过解析）；
2. 判断该符号的某个 `Declarations` 落在「我们的汉语声明文件」里；
3. 若是，在**那个 identifier 节点**上留一个标记。

**标记方式（推荐 a）**
* (a) 加一个 emit flag（如 `EFChineseStdlib`）打到节点上 —— printer 里现成可用：
  `p.emitContext.EmitFlags(node)`；这是全仓既有的机制，改动面最小。
* (b) checker 维护 `map[*ast.IdentifierNode]*ast.Symbol`，经 `EmitResolver` 暴露给 printer —— 更重，且要处理生命周期。

**「我们的汉语声明文件」怎么认**
* 现在：文件名（`汉语标准库-成员.generated.d.ts`）+ 手写的 `汉语标准库.d.ts`；
* 规模化后：应改成**固定的随包 lib 名**（如 `lib.zh.stdlib.d.ts`），并只认这一个名字，避免误判。

**printer 改动点**
* `tsc/internal/printer/printer.go` 的 `emitIdentifierText`：把现在的
  「命中译名表 → 改写」改成「命中译名表 **且** 该节点带 `EFChineseStdlib` → 改写」；
* 全局名（`数学`/`数组`/`控制台`…）走同一条路：它们是 `declare var 数学: Math` 的引用，同样能带标记；
* 于是 六·六 里的「成员名只在成员位置改」这条**收窄规则可以退役**（符号已经足够精确）。

**守卫（必须同时绿，否则不算成立）**
1. **保留**：标准库成员被正确改写（`甲.追加` → `甲.push`）—— 现有判据①–⑤；
2. **新增**：用户自定义成员与标准库译名**同名**时，产物**保留用户的写法**
   （就是教程那次 `编号` 的场景：应当输出 `甲.编号`，而不是 `甲.id`）；
3. 全量九项（尤其 `judge_oss` 英文零回归、`judge_gotest` 全集回归）。

**过渡**：在 (a) 落地前，按 六·六 的结论 —— **暂缓给通用名词定译名**（专用名更安全）。

### 六·七·附：一次未生效的尝试（2026-10-08，已回退，勿重复踩）

**试过什么**：不做符号感知，先加「**文件级安全启发式**」——
在 `printer.go` 里：若**当前源文件**中用户自己声明过同名成员（类/接口成员、访问器、
对象字面量属性、枚举成员），则**放弃改写**。
实现：用 `ast.ForEachChildAndJSDoc` 递归收集名字（该函数**只走直接子节点**，必须自己递归），

**结果：构建通过，但实测不生效** —— 同一文件里明明有 `编号: 数字 = 7;`，
`甲实例.编号` 仍被改写成 `甲实例.id`。（判定第⑩项「同名守卫」全红；构建与其余 9 项正常。）

**待查的三个可能**（下次接手先验证，再决定要不要复活这条路）：
1. `emitIdentifierText` 之外是否**还有别的落盘路径**（属性名不走这里？）——

2. 类属性名 `n.Name().Text()` 是否取得到（`DeclarationName` 的文本来源）；

**结论**：这条路**不值得再赌**；直接做 六·七 的**符号感知**（checker 打标记）更实在。

## 六·八、生成器不管的三类名字（都要手写别名或另想办法）

lib 转换器只扫 `interface` 块，所以下面三类**必须在手写的 `汉语标准库.d.ts` 里补**，
否则守卫⑧会报「有译名无声明」（都已真实踩过）：

1. **全局函数**：`declare function`（如 `createObjectURL`）→ 手写 `declare function 汉语名(...)`；
2. **命名空间里【嵌套的 interface】**（尝试过、未成功，已回退；两个坑记在这里，接手者别再踩）：
   * 收成员时要按「当前嵌套接口」分流，并**用 `nsIfaces[名]` 直接赋值** ——
     写成 `$target = if (...) { $list } else { $members }` 会被 PowerShell **展开**，空表变 `$null`
     （报「不能对值为 Null 的表达式调用方法」）；
   * 嵌套接口头**必须允许泛型**（`interface Global<T extends ValueType = ValueType> {`），
     否则成员会漏到命名空间级、产出孤立声明；
   * ⚠ 一旦把「成员完成」判据加上**花括号配平**（为了处理 `options?: { … }`），
     会把 `interface Array<T>` 的成员整段吞掉（`追加` 声明消失，TS2339）。**根因未查明** ——
     只是加了花括号配平就出现，回退后即恢复正常。
   * 结论：这条线**已回退**，样例译名（`formatToParts`/`resolvedOptions`/`supportedLocalesOf`/`calendar`）
     重新移出译名表。下次做请**先立一个小判据**（断言 `Array` 仍有 `追加`），再动完成判据。
3. **命名空间成员**（如 `declare namespace Intl { interface DateTimeFormat { formatToParts(...) } }`）：
   ⏸ **尚未支持** —— 生成器现在会跳过命名空间里的 `interface`（那是为了避免把 `type X = …` 的
   `type` 当成员名改名），于是嵌套接口的成员拿不到声明。样例译名（`formatToParts`/`resolvedOptions`/
   `supportedLocalesOf`/`calendar`）已**暂时移出译名表**，等支持后再加回。
3. **命名空间成员**：`declare namespace WebAssembly { function instantiate(...) }`
   → ✅ **已支持（2026-10-08）**：生成器也扫 `declare namespace X { … }`，里面的 `function`/`var`
   成员照样出汉语别名（实测产出 `Reflect.定义属性/取原型/含有/是可扩展`、`WebAssembly.实例化`）。
   注意：命名空间里的 `type`/`class`/`interface`/`enum` 是**类型名不是成员**，生成器会跳过
   （曾误把 `type X = …` 的 `type` 改成「种类」产出非法声明，已修）。
3. **构造器对象字面量里的静态成员**：`declare var MediaSource: { new(): MediaSource; isTypeSupported(type: string): boolean }`
   —— 静态方法写在 `declare var` 的**对象字面量类型**里，既不是 interface 也不是 namespace；
   ⏸ **增补方式走不通（已用真编译验证，2026-10-08）**：
   * 对同一 `declare var` 用不同对象类型再声明一次 → **TS2403**
     （`Subsequent variable declarations must have the same type`）；
   * 改用 `declare namespace` 与 `declare var` 合并 → **TS2300**（`Duplicate identifier`）；
   * **结论**：这类静态成员**只能走「复制上游 lib 再改」那条路**（即本方案开头的路线②），
     增补式声明对它无能为力。`isTypeSupported` 已从译名表移出。同类还有 `URL.createObjectURL` 等。
4. **全局对象/类型**：`declare var` / `type`（如 `数学`/`数组`）→ 手写的全局别名块（早已在做）。

### 以下是第 209 轮的错误结论（保留存档，勿据此决策）


对上游（排除 webworker/scripthost）做了一次「还剩哪些**单行完整成员**没译」的统计，结论是：
**剩下的几乎都不是「还没挑到的好名字」，而是「形态上不可用」的东西**：

| 剩下的类别 | 例子（频次） | 为什么不能/不该译 |
|---|---|---|
| 构造签名与内建属性 | `new`(841)、`prototype`(739)、`function`(85) | 不是成员名，是语法/内建；改了会坏 |
| 索引签名残留 | `readonly`(43)、`var`(14)、`in1`(14) | 正则回溯产物，非真成员 |
| 介词/难译 | `from`(56)、`with`(15)、`of`(13) | 汉语无对应短名 |
| 事件属性 `on*` | `onmessage`(8)、`onstatechange`(7) | 多为多行/交叉类型，生成器跳过 |
| 长复合名 | `getElementsByTagNameNS`(8)、`texSubImage2D`(7)、`createElementNS`(7) | 超出 2–6 汉字，或含 ASCII |

**真实可译名**的频次已降到 **7~15**（如 `namedItem`/`willValidate`/`description`/`usage`）。
对照 7687 的完整清单，这说明：**在「只给专用名、不碰通用名词」的策略下，可持续推进的空间已经很小**。

**结论**：覆盖率要再上一个数量级，**只能靠符号感知解锁通用名词**（六·六 / 六·七），
或把目标**收窄**为「高频子集」。继续手写冷门专用名，边际收益已接近零。

## 六·十一、符号感知：侦察结论与实现设计（2026-10-10，长期目标第 1 轮）

### 侦察结论（实证）

* 现在的改写只按**父节点形状**猜（printer.go:1130-1154）：
  ```go
  if english, ok := scanner.ChineseStdlibGlobalName(text); ok { text = english }
  else if isMemberNamePosition(node.Parent) {                 // X.名 / X::名
      if english, ok := scanner.ChineseStdlibMemberName(text); ok { text = english }
  }
  ```
  ⇒ 用户自己的 `甲.描述` 也会被改成 `甲.description`（已发作三次）。
* **emit 管线的 printer 拿不到符号**：`p.IdToSymbol` 只在 `internal/ls/hover.go:461,499` 被赋值，
  那是**语言服务**路径；emit 路径不填。⇒ 想按「符号来自哪个文件」判断，必须**新增**信息通道。

### 选定的实现（比原方案便宜，且安全方向正确）

**「用户声明屏蔽」pass（程序级、纯语法、不需要 checker）**：

1. emit 之前遍历**所有非内嵌 lib** 的源文件，收集其中**声明过的成员名**（属性/方法/接口成员/类字段），
   与汉语成员表取交集 → 得到 `被用户声明的汉语成员名` 集合；
2. 把该集合传进 `PrinterOptions`（新字段），printer 在成员位命中它时**不改写**；
3. **保守方向**：只要用户程序里出现过同名的自声明成员，全程序都不再把它当标准库别名 ——
   宁可让别名被「遮蔽」，也**不静默改坏用户代码**（这正是本项目的红线）；
4. **新增判据**（必须）：一个用户文件里声明 `描述()` 并调用 `甲.描述()`，
   断言产物里**仍是** `.描述`（不被改写）—— 这条今天会失败，实现后必须通过。

相比「checker 逐节点打标记」：不需要类型信息、不受 `--noCheck`/transpile-only 影响、
改动面小（Program 收集 + PrinterOptions 传参 + printer 一处判断）。

## 七、诚实的风险

* 翻译 **7687 个名字**是人力活，且要与**中文 C++ 项目**同词同义（需用户授权去那边只读查表）。
* 生成的 `lib.zh.d.ts` 会随上游 lib 升级而失效 —— 必须靠 `-Check` 逼着重新生成并复核。
* 文本级 emit 改写对「用户自定义同名成员」仍有误改风险（见 `README.md` 待办第 2 条）。
* ⚠ **不要「先翻译、后补声明」**：译名一旦进表，emit 改写就生效，而若声明还没跟上，
  用户用那个汉语名当**自己的标识符**就会被**误改**（例如先加 `字符串→String` 而没加声明，
  用户写 `常量 字符串 = 1` 就会被改成 `String`）。所以顺序必须是
  **先有声明（转换器产出）→ 再加译名 → 再进判定**，每一步同时把名字加进 `judge_zhstdlib` 的用例。
